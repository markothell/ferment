A reply is another round

A reply is a follow-up question put to the whole circle, and everyone takes a turn, as in any round. While it waits for support, it's a spur on the activity it answers. Once it opens and people share, it becomes a node on a branch off that activity. Replies to replies extend the branch. A long chain collapses to its first two replies, a dotted run, and its newest end. Tap anything on the map, then try it as Ines: support Dev's reply, reply to a round yourself, or share in the garden round that's open now.

Shape

What a reply is

A reply is a round. Someone asks the circle a follow-up to something it already explored, and everyone gets a turn to answer. The same rules apply as for any round: one answer each, the same reveal rules and question shapes, and support to get it started. The only difference is where it goes: on a branch off the round it answers, not on the main spiral.

The spiral stays the circle's main line. It still runs from the oldest round outside to what's open now at the center. Branches are side conversations that came out of one round. A branch can grow further when someone replies to a reply, and a round with several replies forks into several branches.

It uses the same lifecycle as any suggestion, so the map uses the same marks. A suggestion is already drawn as a Beet spur off its author's seat. A reply is drawn as the same spur off the activity it answers.

Map

Four states, drawn on the branch

lib/circleMap.ts, pure and tested

  • Where it points. The first spur or node leaves the activity in the direction with the most room. The layout tries 36 directions and keeps the one furthest from other rounds, the thread, other branches and the seat ring, leaning slightly outward. A reply to a reply prefers to continue in its parent's direction, so a chain reads as one branch. The result is deterministic and every coordinate goes through q().
  • From spur to node. The spur is the same 21px mark as the seat spurs. When the round opens, a node takes the spur's place, one gap further out, joined to its parent by a short piece of thread. Reply nodes are drawn at a smaller scale than the main line (radius 2.5 to 6.5 against 6 to 18), on a thinner thread, so the spiral reads first and each branch reads as a side conversation. Within a branch, size still shows how many people shared.
  • Participation lines run from seats to branch nodes, just as they do for spiral nodes. Focusing a branch node lights up its own tellers.
  • Long chains fold. There's no limit on how deep replies can go, but the map shows at most three levels. When a chain runs deeper than that, it shows the first two replies, then a dotted run (●─●··●), then the newest end of the chain. Tapping the dots opens the first hidden reply. The round page's "replying to" trail lists every step.
  • Green is still only for open now. An open reply keeps the live ring on its branch, even while another round holds the center.
Flow

From an activity to a new branch

  1. Reply to this round. Any closed round's page, or the open one after you've shared, has a Reply to this round button. It opens the usual suggest form with PromptFields, headed with the question it answers. The default shape is story. You can also point it at one person's answer ("Esi, say more about the coast"). It's still a round for everyone, with that answer quoted at the top.
  2. It waits as a spur. A Beet spur appears on the activity, and the reply also shows in the circle page's suggestions list with a "replying to …" line. It needs less support than a new question: the author plus one other member is enough, because the circle already cared about the round it answers.
  3. The circle says yes. Once there's enough support, a dot appears at the spur's tip. The host can promote it, the same as any suggestion.
  4. It opens and becomes a node. It goes into the normal queue. settleCircle() opens it when one of the circle's live slots is free (maxLive, default 3), unless the host promotes it sooner. It then sits at the end of its branch with the live ring, and members get the usual "a round opened" notification.
  5. Everyone takes a turn. This is the normal round page and Composer, with nothing new. When it closes, the node turns saffron and it can be replied to in turn.
Rules

What a reply must answer

domain/replies.ts

  • Same circle only. A reply's parent must be a round in the same circle. Open questions to the whole community don't take replies in v1.
  • Only rounds that have happened. The parent must be open or closed. A suggestion can't be replied to, because nobody has answered it yet. On an open parent, you can reply once you can see the answers. On a sealed round, that means after it closes.
  • Who can reply. Anyone who can suggest in the circle can suggest a reply. Who can answer, support and see a reply works exactly as for any other round.
  • Pointing at one answer. The answer must belong to the parent round, and whoever writes the reply must be able to see it under that round's reveal rule.
  • Removing a reply. Withdrawing a waiting reply removes its spur (skipped). Deleting a parent round takes its branch with it.
Data

Two columns

Migration 0001_round_replies

export const rounds = pgTable("rounds", {
  ...
  // Where a suggestion came from, when it was carried over from another round.
  suggestedFromRoundId: text().references(...),
  // The round this one answers. It sits on that round's branch, off the spiral.
  replyToRoundId: text().references((): AnyPgColumn => rounds.id, { onDelete: "cascade" }),
  // Optional: the one answer it follows up on, quoted at the top.
  replyToResponseId: text().references(() => responses.id, { onDelete: "set null" }),
  ...
}, (t) => [
  ...
  index().on(t.replyToRoundId),
  check("rounds_reply_not_self", sql`${t.replyToRoundId} is distinct from ${t.id}`),
  check("rounds_answer_needs_round", sql`${t.replyToResponseId} is null or ${t.replyToRoundId} is not null`),
]);

How it differs from suggestedFromRoundId. That column is lineage: a question carried in from somewhere else, and it still joins the spiral. replyToRoundId is placement: the round belongs on another round's branch. A reply can have both.

Domain. suggestReply() in domain/replies.ts checks the parent against the rules above, then calls suggestRound() with the new field. rounds.ts gains the two parameters and passes them to the insert. approvalsNeeded() also takes a reply flag, which caps the requirement at 2. circleRounds() returns replyToRoundId, so MapRound carries it through to the layout.
